## Building a Telecom BSS on AWS EKS — and What Broke Along the Way

I picked up a scaffolded telecom BSS (Business Support System) — five Spring Boot microservices
aligned to TM Forum Open APIs, a Terraform-managed EKS platform, a full CI/CD pipeline — and spent
the last several months turning it from "code that compiles" into "infrastructure that has
actually run, broken, and recovered on real AWS." This post is about the second part.

### The system

- **5 backend services** (Java 21 / Spring Boot 3.2), each owning its own Postgres schema:
  `customer-service` (TMF629), `product-catalog` (TMF620), `order-management` (TMF622, with a
  transactional outbox), `billing-service` (TMF678, with an idempotent SQS consumer), and
  `api-gateway` in front of all of them.
- **Async by design**: `order-management` publishes `OrderCompleted` to EventBridge; a per-consumer
  SQS queue (with a DLQ) feeds `billing-service`. No service calls another service's database.
- **Infrastructure as code**: Terraform across `dev`/`staging`/`prod`, each its own VPC/EKS/RDS,
  wired through IRSA (per-service IAM, no shared credentials) and GitHub OIDC (no static AWS keys
  anywhere in CI).

### What "done" actually meant

The scaffold looked complete on paper. It wasn't running. Docker builds failed, Terraform didn't
`init`, integration tests had never executed against a real database, and — the one I'll come back
to — a dedup mechanism that looked correct in code review had never actually prevented a duplicate.
None of that is a criticism of a fast scaffold; it's the normal gap between "designed" and
"verified," and closing that gap became the actual work.

Every phase in this project ends with something measured, not assumed:

- `terraform apply` on a from-scratch AWS account → `kubectl get nodes` showing real EC2 instances.
- An order placed through a real browser, through a real ALB, producing a real invoice with the
  correct 10% VAT — proving the EventBridge → SQS → billing chain actually works with IRSA
  credentials, not LocalStack's static test keys.
- A CI pipeline whose green checkmark I stopped trusting until I'd read `Tests run > 0` in the log
  — because I'd already been burned once (see below).

### The bug that taught me the most

A dedup table (`event_id` as primary key) was supposed to stop a redelivered SQS message from
creating a second invoice. It compiled. It reviewed cleanly. The integration test for it was
**green**. It did not work — for about four months.

The reason: the primary key was assigned in application code, not generated by the database. Spring
Data JPA's `save()` on an entity with a manually-assigned ID doesn't know whether that's an insert
or an update, and defaults to `merge()` — which upserts happily instead of throwing on a duplicate
key. The mechanism's entire premise (a duplicate insert throws) was quietly false. Nobody saw it
because the integration test relied on Testcontainers, which was blocked by a local Docker Desktop
issue for weeks — so the "green" test had never actually executed until CI ran it for real, months
later, on a Linux runner.

The lesson I keep coming back to: **a green CI check tells you a test passed, not that it ran.**
Read the test count. Full writeup: [`docs/POSTMORTEMS.md`](POSTMORTEMS.md).

### What I decided *not* to build

Not every scaffolded idea survived contact with reality. The original design called for Karpenter
to auto-provision Spot instances for ~70% savings. But every environment here is **ephemeral** —
stood up for a session, torn down right after — which already captures most of the cost benefit
Karpenter would add, while its extra moving parts (two new CRDs, an interruption-handling IAM role,
replacing a managed node group that was already working) would have added risk right before the
one phase where I needed *stable, reproducible* load-test numbers. Full reasoning in
[ADR-007](adr/ADR-007-karpenter.md) — sometimes the right engineering decision is writing down why
you're *not* doing something.
